A · 链路断裂 —— 数据产生了，但走不到消费者，或消费者根本不存在
1
整条崩溃恢复链路是死代码 persist.rs:144 · core.rs:123
persist::restore() 在全 crate 没有任何调用者；CoreDeps.restored 从未被设成 Some。15 个链路场景一个都没走过它。你说的「退出应用后再打开进展丢失」在当前实现里不是风险，是必然。

2
即使恢复了，对话历史也拿不回来 core.rs:225
Restored.replayed 里的 msgs 被丢弃，Core::start 硬编码 history: Vec::new()。恢复后推断图在、对话没了 —— 这是最糟的一种恢复：模型看到一张自己不记得怎么推出来的图。
history 与推断图从同一份 event log 重放，不存在只恢复一半的可能。
3
turn 跑到一半退出 = 本轮一个字节都没落盘 core.rs:434–448
落盘只发生在 TurnFinished。在那之前，用户的输入、模型已经流出来的正文、已经 propose 的 ops，全部只在内存。用户等了两分钟看着正文往外吐，关掉应用，回来一片空白。
落盘粒度从「轮」改成「事件」：用户输入在进 inbox 的同一刻就已提交事务。
4
Shutdown 不 flush core.rs:332–337
CoreMsg::Shutdown 直接 return false：跳过 TurnFinished，也不等 writer 排空队列。优雅退出和被 kill 的效果一样。
Shutdown 变两段：cancel 并等 TurnFinished（带超时），再等 writer 确认 flush。
5
inbox 不持久 core.rs:180
用户在 turn 运行中插了三句话，还在队列里没被取走，进程没了 —— 三句话消失，而且用户以为已经发出去了。
用户输入落盘后才给 UI ack；未被消费的输入在恢复时重新进 inbox。
6
恢复会把用户填的字段变成模型推断 persist.rs:164
HistoryRecord.commits 根本没存 origin，restore() 把重放的 op 一律记成 Origin::Model。于是 [用户设定] 标记在恢复后消失 —— 而「模型改用户填过的字段前先问」这条约束的全部落点就是那个标记。删掉锁之后剩下的唯一保护，在崩溃恢复后失效。
origin 是 op 的固有属性，跟 op 一起进事件体，不由重放方推断。
7
上下文折叠不落盘 core.rs:403–422
CompactHistory 只改内存。恢复后折叠白做，下一轮再花一次摘要的钱；而且内存历史与盘上历史长度从此不一致，没有任何记录说明折叠发生在哪。
折叠是一条追加事件 fold{from_seq,to_seq,summary}，原文永不删除 —— 顺带让 UI 能「展开被折叠的部分」。
11
TurnStats 收下即丢弃 core.rs:434
TurnOutcome.stats 到了 Core，handle 只用了 msgs 和 aborted。验收方案的副指标「干预次数」现在拿不到，判断段耗时占比、插话次数、工具超时数也一样 —— 全部在这一行蒸发。
turn 表一行一轮，stats 存 JSON；SessionApi::report() 是它的第一个消费者。

CoreMetrics 不落盘也不发 UI core.rs:52
四个异常指标（stale_msg / refuse_inj / stale_op / pend_drop）设计意图是「不是 0 就说明有竞态」，但只在进程退出时的 CoreSummary 里可见。作为运行时告警完全用不上。
每轮末写一行 metric，并推一条 UiEvent 让状态栏能亮。
13
CostLedger 不落盘 cost.rs:14
R6 的账目只在进程内，重启归零，跨会话总花费拿不到。而「判断段占总 token 的 X%」这句话恰恰需要足够多的样本才有说服力。

B · 语义不一致 —— 同一事实两处存储，或声明与实现对不上
8
touched 声明「一轮」，实现是「一辈子」 core.rs:177
注释写「作用域天然只有一轮」，但 HashMap<Path,Version> 从不清空，长会话下每个被用户编辑过的 path 永久驻留。更根本的是它是 Field.version + Field.origin 的冗余副本 —— 同一个事实存了两份，改一次语义要动两处。
收窄成「本轮内被用户改过的 path 集合」，turn 开始时清空；Op::Remove 留一条墓碑事件承载版本。
9
scene / scene_overrides 生命周期错位 state.rs:171–174
scene 是 turn 级瞬时量、scene_overrides 是审计流水，两者却都塞进跨会话持久的推断图里，同走一个 version、每次快照整份重写。结果之一：重启后 UI 显示上一次会话最后一轮的场景。
两者都从 Workspace 删除，改成事件（scene / scene_override）。UI 要当前场景就查最近一条。
10
turn 手里的快照与 Core 的 ws 在轮中分叉 turn.rs:166 ↔ core.rs:359–382
这就是你说的「场景选择后再塞进来比较奇怪」。SceneDecided / Questions 写进 Core 的 ws，但 turn 的 snap 是轮初取的，后面 mk_context 用的还是旧值 —— 同一份数据在同一时刻有两个不同的值，而且没有任何机制说明哪个算数。
把两个概念拆开命名：TurnInput（整轮不变的只读输入）与 WorkspaceView（Core 的当前物化视图）。turn 只往外追加事件，永远不往 TurnInput 里回灌。
22
Version 三重身份，且部分 bump 不落盘 ids.rs:16 · core.rs:313/321/366/376
同一个数同时是 CAS 令牌、崩溃恢复游标、UI 版本显示。而 SceneDecided / Questions / OverrideScene 都 bump 了 version 却不 emit_snapshot，盘上 version 长期落后于内存 version。
改成事件流的 seq：一个数一个语义 —— 它是「第几条事件」，CAS 比它、恢复从它开始、UI 显示它、R5 回滚锚定它，全都是同一件事的不同用法。
23
restore 的边界判断在 pending 为空时会多算一版 persist.rs:155
if rec.version < version { continue } 用的是严格小于。正常路径 AppendHistory(V) → commit bump 到 V+1 → snapshot(V+1) 没问题；但 pending 为空时 commit_pending 返回 0 且不 bump，snapshot 写的还是 V，那条记录会被重放，version.bump() 让恢复后的版本比实际大 1。
seq 由存储层单调分配，重放不再自己 bump，边界问题从结构上消失。
14
open / parked 静默覆盖，且用户根本改不了 msg.rs:108–117 · state.rs:210
Questions 整份覆盖，没有冲突裁决也没有 rejected 反馈：用户在侧栏往待落定里加了一条，模型这一轮结束时整份盖掉，用户和模型都不会知道。而且 Op 只能改 fields，UI 上这两个列表实际是只读的 —— 跟「待落定区是用户整理思路的地方」正好相反。
open / parked 走与 fields 同一条 op 通道，每条带 item_id，享受同一套 Stale 裁决。

client_id 去重只在内存 core.rs:186
LruSet 重启后清空。UI 在超时后重发同一条（这正是 client_id 存在的理由），跨了一次重启就会重复处理。
去重表落库，主键就是 client_id。

§5

SQLite schema

一个 workspace 一个 store.db，表里带 session_id —— 不是一个会话一个文件，因为跨会话的成本汇总、找历史会话、蒸馏读多个会话都需要联查；会话隔离靠索引不靠文件边界。

-- 打开时设定。WAL 让「UI 读」和「writer 写」互不阻塞，这是引入 SQLite 最直接的收益。
PRAGMA journal_mode = WAL;
PRAGMA synchronous  = NORMAL;   -- WAL 下崩溃安全；掉电最多丢最后一个未 checkpoint 的事务
PRAGMA foreign_keys = ON;

-- ═══ 唯一真相 ═══════════════════════════════════════
CREATE TABLE event (
  seq        INTEGER PRIMARY KEY AUTOINCREMENT,  -- 全库单调。取代 Version，一个数一个语义
  session_id TEXT    NOT NULL,
  turn_id    INTEGER,                            -- NULL = 不属于任何一轮（用户编辑、phase 推进）
  at_ms      INTEGER NOT NULL,
  kind       TEXT    NOT NULL,   -- user_input | answer | op | scene | scene_override |
                                 -- message | delta | fold | phase | question | tool | cost |
                                 -- turn_start | turn_end
  actor      TEXT    NOT NULL,   -- user | judge | answer | subagent | tool | system
  body       TEXT    NOT NULL    -- JSON，按 kind 定形状
);
CREATE INDEX event_sess_seq ON event(session_id, seq);
CREATE INDEX event_turn     ON event(turn_id, seq);
CREATE INDEX event_kind     ON event(session_id, kind, seq);

§6

落盘时机与 cache

Core 依然不碰磁盘。变的是落盘的粒度（轮 → 事件）与确认语义（无 → 分两级）。

Core.handle(msg)            ── 同步、微秒级、不 await ──
  ├ 分配 seq（向 Store 预留一段，或由 Store 回填）
  ├ 折叠进内存物化视图（Workspace / CostLedger / open_questions）
  ├ 推 UiEvent（带 seq）
  └ 发 WriteJob{ events, flush } 给 writer

writer task（独占 SQLite 写连接，spawn_blocking 里跑 rusqlite）
  ├ must-flush  ── 立刻开事务、提交、回 oneshot ack
  │    用户输入 · 用户编辑 · 用户回答 · turn 结束 · phase 推进 · shutdown
  └ best-effort ── 攒到 ≤64 条或 ≤200ms 再一个事务写掉
       正文 delta · 工具事件 · cost · scene · metric

分两级的理由：must-flush 的那些是用户已经付出过动作的数据，丢了用户会知道并且会生气；best-effort 的那些是模型产物，掉电丢掉最后 200ms 的正文，代价只是重生成。全部 must-flush 会让每个 delta 都开一次事务，全部 best-effort 就回到了「用户输入还在内存里」的老问题。

UI 的 ack 语义

SessionApi::send 在 writer 事务提交后才返回 Ack{seq}。UI 在此之前把气泡显示成「发送中」。这一条直接解掉缺陷 5：用户看到消息变成已送达，就意味着它已经在盘上了。

Core 内存里保留什么

缓存形态为什么是这个形态失效 / 重建
Workspace可变结构体推断图是 CAS 的仲裁对象，必须在 Core 手里且随时可读启动时 snapshot + replay
historyArc<Vec<Message>>全量上下文策略要求每轮拿到全部。Arc::make_mut 追加，turn 取 Arc clone 是 O(1) —— 解掉缺陷 16 的每轮深拷贝同上；折叠只换 Arc 内容
CostLedger聚合计数UI 状态栏每次 CostTick 都要显示总额，不能每次去 SQL 求和启动时一次 SUM 查询

MemoryArc<Memory>，只读owner 是用户，Core 只读不写会话启动时重读；文件变更暂不热加载

快照写入频率

每 200 条事件或每轮结束写一份，保留最近 10 份。快照纯粹是启动加速，写失败只记一条告警不影响任何正确性 —— 这是把 snapshot 从「崩溃安全的一半」降级成「cache」之后拿到的自由度。

「一个 turn 只存一个 snapshot」这句话在新结构里不成立了 —— 因为 snapshot 不再是 turn 的产物。turn 只做一件事：往 event log 追加。snapshot 是 Core 对 event log 的定期折叠，跟 turn 边界完全解耦。turn 手里那份改名叫 TurnInput，它是整轮不变的只读输入，从此不会有「场景选完了再往里塞一个字段」这种事 —— 场景判定是一条出向事件，不回灌。

ask_user 为什么仍然不阻塞

工具不等用户，这一条不变：阻塞会让 turn 挂在人类时间尺度的等待上，打断、插话、落盘全都得排队。变的是回答能被认领 —— 提问有 id、有持久状态，回答带着 id 回来，注入时告诉模型这是对哪个问题的答复。现在的实现里这层绑定完全没有，模型只能靠猜。

§8

接口封装

现在 CoreHandle 上 UI 侧和 turn 侧的方法混在一起，四个 emit 类方法四种签名，读接口只有一个「返回一切」的 snapshot()。拆成四个面，各自只服务一类调用方。

// ── 给 UI：axum / WebSocket handler 只认这一个 ─────────────────
pub trait SessionApi {
    // 写：全部返回 Ack{seq}，且在落盘事务提交后才返回
    async fn send(&self, text: String, mode: SendMode) -> Result<Ack>;
    async fn answer(&self, q: QuestionId, choice: String) -> Result<Ack>;
    async fn edit(&self, ops: Vec<Op>) -> Result<ApplyReport>;   // 不再要 base_version
    async fn interrupt(&self) -> Result<Ack>;
    async fn advance_phase(&self, to: Phase) -> Result<Ack>;
    async fn override_scene(&self, to: SceneId) -> Result<Ack>;
    async fn distill(&self) -> Result<DraftPath>;

    // 读：分开，不再有一个「返回一切」的 snapshot
    async fn workspace(&self) -> Arc<WorkspaceView>;        // 小，不含 history
    async fn messages(&self, r: SeqRange) -> Vec<Message>;   // 分页；含被折叠的原文
    async fn open_questions(&self) -> Vec<Question>;
    async fn report(&self) -> SessionReport;                 // R6：cost + stats + metrics
    fn subscribe(&self) -> broadcast::Receiver<UiEvent>;      // 事件带 seq，跳号即补拉
}

// ── 给 turn task ────────────────────────────────────────────
pub trait TurnApi {
    async fn input(&self, turn: TurnId) -> Option<TurnInput>;  // 整轮一次，只读，不回灌
    async fn take_injections(&self, turn: TurnId) -> Vec<Injection>;
    async fn propose(&self, turn: TurnId, ops: Vec<Op>) -> ApplyReport;
    async fn emit(&self, turn: TurnId, ev: TurnEvent);        // 一个方法替掉四个
    async fn finished(&self, turn: TurnId, out: TurnOutcome);
}

// scene_decided / questions / compact_history / cost 四个签名不同的方法合并成一个枚举，
// 因为它们本来就是同一件事：turn 往 event log 追加一条。
pub enum TurnEvent {
    Message(Message), Delta(String), Scene{ id: SceneId, rationale: String },
    Fold{ from: Seq, to: Seq, summary: String }, Tool(ToolRecord),
    Cost{ role: Role, task: Option<TaskId>, usage: Usage },
}

// 插话与提问回答类型化 —— 现在两者都退化成 Message::user，模型分不出来
pub enum Injection {
    Said{ seq: Seq, text: String },
    Answered{ seq: Seq, question: QuestionId, choice: String },
}

// ── 给存储：SQLite 是一个实现，MemStore 是另一个，FaultStore 是第三个 ──
pub trait Store: Send + Sync {
    async fn append(&self, batch: Vec<EventIn>, flush: Flush) -> Result<Seq, StoreError>;
    async fn load_snapshot(&self, s: SessionId) -> Result<Option<(Seq, Workspace)>>;
    async fn put_snapshot(&self, s: SessionId, seq: Seq, ws: &Workspace) -> Result<()>;
    async fn replay(&self, s: SessionId, from: Seq) -> Result<Vec<Event>>;
    async fn messages(&self, s: SessionId, r: SeqRange) -> Result<Vec<Message>>;
    async fn report(&self, s: SessionId) -> Result<SessionReport>;
}

故障注入

  • FaultStore 包一层 Store：按随机种子在第 K 次 append / flush 注入 Err、写一半、延迟 500ms、SQLITE_BUSY。断言：Core 不 panic、发出 PersistDegraded、用户仍能继续对话。

best-effort 攒批意味着「刚发生的事还没在盘上」，没有能等的点 S03/S18/S19/S20 一开始全红 —— 断言读盘时事件还在 writer 的缓冲里 加 CoreMsg::Flush / session_flush()：一个空的 must-flush 批次当屏障。生产上也用得着（退出确认、「已保存」提示）
TurnClosed 走 best-effort ⇒ 崩在它之后会把一轮好好结束的对话标成 crashed 写 S13 的崩溃恢复断言时想到的 改成 must-flush。它是「这一轮真的收完了」的凭据
恢复补的修补事件走 best-effort ⇒ 下次启动还要再判一次「上次崩了」 S13 的「未闭合调用被补上了 Aborted」断言红了 同上，改成 must-flush
turn 需要本轮的局部时间线来拼下一次 prompt 写 turn.rs 时发现：TurnInput.events 是轮初的快照，turn 自己 emit 的东西不在里面。让 turn 自己把 Emit 映射成 Body 会造出第二份映射 Applied 回带 events —— Core 追加进去的那几条原样返回，turn 直接并进 local。映射只有一处
插话回到 turn 时会退化成一条普通消息 同上。原设计的 Vec<UserMsg> 又要 turn 再映射一次 take_injections 直接返回 Vec<Event> —— 它们在用户按发送时就已落盘，本来就是时间线上的事件
serde 的内部 tag 叫 kind，与 Returned.kind 字段撞名 编译器报的 字段改名 outcome，比 kind 也更准
