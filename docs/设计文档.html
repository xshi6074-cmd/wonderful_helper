Premortem

缩小从一个模糊待验证的 idea，到能交给编码 agent 写实验代码的实验设计方案之间的 gap，打造更个性化的research workspace。

一痛点分析

随着agent能力变强，research student可以将自己更多的模糊idea交给agent设计实验和验证。但是实际使用的过程中，agent时常不追问模糊方案中的设计偏差，设计空白或设计失误要在实验结果不好时才能暴露，之后仍需多轮调整，费时费力。经过反思，原因可能如下：

  1. 刚刚开始科研的学生经验不足，仅有的一些经验分散在对话里，涉及到交互、基础知识、细节问题等诸多方面，无法分清。
  2. 与agent不能及时地对齐意图：任务交给agent执行后学生自己对流程失去了清晰的把握，设计不完全，对错误的感知变弱。
  3. Agent memory不完全适配学习需求。通用 agent 的 memory 多是命令执行要求或长期用户画像。
  4. 当前给出模糊需求让 agent 独立完成全权设计，稳定性、准确性尚低。agent通常对设计好的部分执行更好，其它部分“跑通就行”。

所以理想的agent形态应该能分类、整理、复用学生的经验；与用户进行快速的意图对齐，把需要反复强调的提示词流程化；拥有灵活和个性化的记忆管理机制

二场景定制方案

设计"场景分流"机制，在对话前先判断当前是否命中某些经验的相似场景，将相应经验灌入上下文供agent参考。同时给对话提供一键蒸馏，形成经验闭环。用户也可以选择蒸馏与其它agent的协作记录，选择保存。

维护一层工作memory：把梳理架构图固定为必须执行的动作，要求agent设计时考虑完整实验链路，对于未定部分诚实标出；用户可以随时修改架构图，同时随每轮对话对实验设计有清晰把握，有利于意图快速对齐。显示维护待决策和已经决策的部分，减少错过设计要点的可能。

强调个性化：分设行动和探索两种模式，对于希望快速落实方案的场景在不损失精度的情况下要求agent对用户精准发问，减少交互；对于用户希望拓展学习的场景鼓励agent进行发散和开放式提问。所有prompt方便修改，经验场景易于插拔。

三特色功能详述

以下功能分别对应架构图中的 state、model、UI 与 tool call 接口。Core 不替模型决定研究流程，主要负责把这些接口接成一条可恢复、可打断、写入顺序确定的协作链路。

核心功能

实验流程图：用户和模型看的是同一张图

讨论实验时最难发现的偏差，是双方对“实验现在长什么样”理解不同，却谁都没有意识到。Premortem 让回答模型把完整实验链路画成一张结构化流程图放在侧栏；用户直接在图上点选、修改。这张图同时是模型下一轮上下文里的那一份，所以用户纠正一次，双方就对齐一次，不必在长对话里反复重申。

  • 形状和颜色都有含义。数据、模块、算子、损失、指标、注记各有固定形状与材料色；流向、监督、对照、依赖用不同线型区分。形状词表在 prompts.toml 中，用户可以改。
  • 哪里是猜的一眼可见。有依据的画实线，模型推测的画虚线，用户定下的描紫色粗边。虚线的地方，就是需要确认的盲区。
  • 点一下就能改。点节点可以改标题、类型、细节或直接删除；点边可以改说明和关系类型。展开大画布后支持缩放、ELK / Dagre 布局切换，以及查看 Mermaid 源码。
  • 不会被旧快照冲掉。用户的编辑立即写入事件时间线；同一轮里，模型基于旧图对同一元素的修改会被 core 拒绝，不会把刚纠正的内容改回去。

1 · Memory：把当前理解与长期经验分开

层保存内容更新方式生命周期
推断层 / working memory 实验结构图、图外关键字段、待落定项、搁置项与本轮场景 回答模型调用 record_graph / record_note；用户在侧栏修改已有内容 属于一条会话，随事件时间线保存并可在重启后恢复
持久层 项目概述与进展、合作偏好、知识状态、场景目录、提示词与真实案例 用户直接编辑 Markdown / TOML，或确认一键蒸馏生成的草稿 跨会话；新对话开始时重新装载

推断层不是对话摘要，而是系统对“当前实验设计”的结构化理解。图用节点和边表达数据、模块、算子、监督、指标与依赖关系；不适合塞进图里的目标、约束、决定理由和验证口径放在图外字段中。待落定与搁置分开维护，使“现在必须决定”与“有价值但暂不展开”不会混在一起。

模型读到仓库事实或形成新候选后，可局部更新图和笔记，不必重画整张图。节点和边保留来源与置信度，界面用“有依据 / 模型猜测 / 用户确定”区分状态；结构化图在前端绘制成可点击 SVG，并提供展开画布、ELK / Dagre 布局切换与 Mermaid 源码查看。用户对已有节点、边和清单的编辑立即进入同一条事件时间线。

Core 独占会话状态写权：模型动作与用户编辑都按事件顺序提交。同一轮中，如果用户已经改过某个对象，模型基于旧快照提交的冲突修改会被拒绝，避免流式生成期间把用户刚刚纠正的内容覆盖掉。SQLite 中保存的是 append-only 事件；checkpoint 只用于加速恢复，工作区视图可由事件重新物化。

持久层承担另一种任务：让一个新对话迅速知道项目做到哪里、用户怎样协作、哪些知识已经讲过，以及过去哪些错误值得在相似场景中提前检查。文件在每轮开始时重新读取，因此用户通过界面修改后，下一轮即可生效；它不会被普通回答自动改写。

2 · 经验卡片：让一次踩坑变成下一次的检查入口

系统把可复用经验组织为“场景卡片”。一张卡片在逻辑上由两部分组成：playbook.toml 中的触发条件与核查方法，以及 cases/*.md 中与该场景关联的真实案例。规则负责迁移，案例保留当时的具体上下文和证据边界。

卡片字段作用
when描述什么可见信号值得触发，并写明不该触发的情况，避免每轮都套同一张卡
guidance给回答模型一套具体核查方法，例如沿生产者—变换—消费者检查接口语义
tools补充该场景下可暴露的工具；只决定“能用什么”，不强制调用顺序
cases保存真实经历中的目标、遗漏、修正、结果与适用边界，为规则提供例证

模型选择。每轮正式回答前，判断模型只读取场景目录和当前上下文，返回最多三个场景及简短理由；它不检索资料，也不提前写推断。Core 随后把命中卡片的 guidance、相关案例和工具说明注入回答段。判断、回答和蒸馏角色可在配置页分别选择 provider 与模型，因此简单的场景分类不必占用与正式回答相同的模型。

用户选择。当前场景与判定理由显示在对话顶栏。用户可以点开场景标签，多选或替换下一轮要采用的卡片；用户选择优先于判断模型。覆盖动作会进入时间线，但不会在已经运行的回答中途更换 prompt，从而保证同一轮前后一致。

一键蒸馏。用户主动点击后，蒸馏角色读取完整会话时间线、当前 working memory 与已有持久记忆，生成按目标文件分节的更新草稿。项目进展、合作偏好与知识状态采用完整替换草稿；场景库只给出按 ID 合并的新增或更新卡片；案例单独成文件。界面允许逐节预览、修改和勾选，只有通过格式与冲突校验并由用户点击写入的部分才进入持久层。这里沉淀的是可复用经验，不是让模型权重自动“学习”一次对话。

3 · 用户体验：把关键选择做成轻量交互

探索 / 行动模式。顶栏提供显式切换。探索模式允许原理说明、候选比较和开放式追问；行动模式关闭主动教学类场景，把注意力放在实现接口、训练时序、评估与交付缺口。两种模式分别配置提示词和工具使用说明，切换由用户发起，并在下一轮统一生效。

选择题工具。当目标、预算或偏好确实需要用户决定时，回答模型可以调用 ask_user，展示 2—4 个带有实际差异的选项。提问本身会持久化；点击选项后，回答作为下一轮的普通用户输入进入上下文。工具不会让当前 turn 挂起等待人类，因此停止、刷新与会话恢复仍能正常工作。

对话控制。正文通过 WebSocket 流式显示，工具调用显示进行状态；用户可以停止当前轮次。CancellationToken 会把停止信号传播到模型调用和工具任务，已经提交的推断与已经收到的正文仍然保留。会话列表支持保存、恢复与从指定 turn 分支，方便比较不同设计路线而不覆盖原历史。

配置入口。判断、回答、subagent 三个角色的 provider、model、温度和输出上限可分别配置；持久记忆、场景卡片、提示词和本地工具授权目录均能在界面中查看或修改。常用选择留在主界面，高级配置集中在侧栏，避免把模型参数与研究讨论混在一起。

4 · 工具调用：只读材料，按需回灌

本地读取不是一个裸 shell，而是一组可组合的只读工具。模型先看项目轮廓，再按文件名或符号缩小范围，最后分页读取真正支撑结论的片段。它们共同支持扫读授权目录中的代码与文本材料，并把相关结构或要点写入当前 working memory；当前实现不提供通用 PDF、Office 文档或二进制文件解析。

工具用途边界
repo_tree按深度查看目录结构并统计文件类型，定位项目入口尊重 .gitignore，不跟随符号链接，输出受条数和深度上限约束
fs_find用 glob 按文件名、后缀或目录模式定位文件未命中只说明当前授权范围和忽略规则下未找到
fs_grep用正则检索文本并返回真实路径与行号匹配结果用于定位；判断控制流仍需继续读取上下文
fs_read从指定行开始分页读取文本文件单文件、单次返回和行数均有限制，截断时给出续读位置
web_fetch抓取已知 URL，抽取正文并转为保留标题、列表、代码、表格和链接的 Markdown不是搜索引擎；不保证登录页、动态页面或 PDF 可解析

web_fetch 不把未知长度的网页全文直接塞进模型上下文。正文先保存到 workspace/，工具只返回网页信息、文本前缀和本地路径；模型需要更多内容时，再用 fs_read 分页或 fs_grep 定位。这让网页大小不会意外吞掉整轮上下文。

工具注册表根据当前场景、模式和配置决定回答模型能看到哪些能力。独立的只读调用可并行，动作工具和提问按顺序提交；调度层统一处理超时、心跳、取消与结果保序。路径需落在用户授权目录内，联网受协议、域名、重定向和响应体上限约束；模型没有裸 shell，也没有任意写文件工具。

功能闭环：读取本地或网页事实 → 写入实时 working memory → 通过场景卡片与选择题暴露关键问题 → 用户确认或修正 → 一键蒸馏为下一次可复用的持久经验。

四系统架构

core 负责调度与写权仲裁。UI、模型、tool call、state 分别作为接口插入 core；SQLite 事件时间线是事实源，workspace 是可由事件重建的会话物化视图。
