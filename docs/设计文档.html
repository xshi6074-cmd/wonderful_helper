Premortem

缩小从一个模糊待验证的 idea，到能交给编码 agent 写实验代码的实验设计方案之间的 gap。

一痛点分析

选题来源于一个刚入门的科研新手需要 agent 辅助落实实验代码的场景。基于 Codex / Claude Code 的 agent 有很强的执行和编码能力，使用者看起来手上有很强力的工具，但从一个模糊待验证的 idea 到跑出实验结果能验证或证伪这个 idea，中间有很大 gap，需要反复试错、与 agent 频繁交互调整来填平。原因大致是下面这些：

  1. 科研新手对自己的领域认识不全，容易给出一个模糊、比较偏离正轨的实验思路就让 agent 照此实现；或者不熟悉实验链路和各模块适配情况，浅读论文给出一些胡乱拼凑的实验设计。
  2. Agent 执行强，但权衡判断不主动，很可能盲目执行、过度执行。
  3. Agent 一般不维持关于用户学习状态、对项目认识状态的工作记忆。通用 agent 的 memory 多是命令执行要求或长期用户画像。
  4. 当前给出模糊需求让 agent 独立完成全权设计，稳定性、准确性尚低，具体权衡仍然需要 human in loop。

但 agent 编码能力相对可信。所以需要用户反复试错并调整与 agent 的交互方式，或者让这些调整和判断的经验被 agent 学习吸收为固定流程。

二定位与设计思路

实现一个 agent，用于缩小从模糊待验证的 idea 到能交给编码 agent 写实验代码的实验设计方案之间的 gap。它不写实验代码，也不替用户做决定。

每一轮先判断当前处于哪一种协作场景，据此注入该场景对应的约束、建议与参考案例，并暴露该场景下可用的工具，然后生成回复。同时更新持久记忆、维护用户能随时修改的实验方案推断。场景在多轮协作中持续判定：当前需要的是补充领域背景、澄清目标、追踪代码链路、检查假设、发散设计、优先低成本试验，还是及时停止讨论并进入实现。场景、指令、参考案例与工具集都依个人经验自定义。

三条贯穿全局的约束：

  • Agent 不主导流程。推断随交互自由更新；推断图上标出每个字段的出处，模型改动用户填过的字段之前先在正文里询问；进入实现由用户拍板。
  • 判断的优先级高于回复。每轮先判断场景，判断结果决定这一轮用什么约束、给什么案例、开放哪些工具，然后才生成回复。
  • 判断决定注入什么，不决定做什么。harness 把工具与呈现形式摆出来，用不用、用几次、什么顺序由模型决定。每句话要能说清它服务于哪个尚未落定的问题。

三功能

1 · 推断架构图

模型通读实验代码库，结合对用户实验需求的推断画架构图并呈现在对话侧边栏，用户可随时修改。底层存结构化数据（节点、边、属性），渲染层负责画图：模型修改数据，用户在侧栏点选节点编辑字段，两边都不接触画图语法。

节点与边可标注来源与置信度。来源是仓库位置、论文章节、用户口述或模型推测；未标来源与标为模型推测的在图上以虚线区分。图中有逻辑不顺或缺失的部分能让用户意识到盲区，也便于用户和 agent 快速对齐。

写权归 core 唯一所有。模型的改动先进入本轮的未提交区，turn 结束时一次提交；用户的编辑立即生效并落盘，不随 turn 回滚。

2 · 协作场景

每轮由模型判断当前场景。harness 据此做三件事：注入该场景的约束与建议、注入命中的参考案例、暴露该场景下的工具。之后由模型自行决定说什么、调用哪些工具、调用几次。界面显示本轮所选场景与判定理由，并支持一键更换，更换记录用于修正场景描述。

提问同样是一个工具。模型可选择提出选择题等不同询问方式。

场景目录是配置文件，用户随时可改。新增一个场景或替换整份目录都不需要改代码。

3 · 记忆与持久层

层内容形态
持久层 项目总体概述、阶段目标、进展（跑通并成立的与试过没成立的实验方法概述）；用户的合作偏好；用户的实验相关知识情况与经验评估；易犯错场景目录与对应指令；参考案例 跨会话。Markdown 与 TOML 文件，用户随时直接编辑
推断层 推断图；本轮场景 一次会话。turn 是它的事务边界

持久层的目标是让一个新对话能快速入手这个项目。首次运行时把初始内容写成文件，之后读到的就是用户改过的版本。

知识与经验评估用三档决定 agent 是提问还是讲解：有储备则提问；明确没有储备则先讲通机制再把判断交回；储备情况不清楚时先问清楚这一点本身。

4 · 模式选择

探索 mode行动 mode
可用场景全集，含讲解与开放式追问关闭讲解类场景
资料抽取目标领域知识、动机、术语方法、超参、实现细节

mode 由用户显式切换。

5 · 一键蒸馏

用户在一段会话结束后触发蒸馏。subagent 读全程对话与推断图，产出持久层的更新草稿：项目进展、这次显现的合作偏好、知识与经验评估的更新、值得入库的易犯错场景与指令。草稿写成独立文件，用户看过、改过再合并进持久层。

四场景定制方案

定制一 · 判断与回答分离的两段式循环

解决：通用 agent 由模型自行决定要不要提问，"尽快收敛到可执行"的目标会压制提问倾向，问题只在撞墙后暴露。

做法：harness 强制每轮先跑判断段，产出场景判定与推断 diff；据此注入约束、案例与工具集，再跑回答段。判断段不带任何场景的指令全文与案例，可配便宜模型。场景目录与案例库为可插拔配置。

对比示例：同一个模糊 idea，通用 agent 直接给出的实现方案，与本系统在动手前提出的第一个问题。

定制二 · 结构化架构图推断

解决：新手判断不了 agent 给的设计对不对，也意识不到 agent 误解了什么。

做法：推断以带来源标注的结构化架构图承载，由仓库问答 subagent 从真实代码填充；未标来源的节点在图上显式区分。

对比示例：同一个仓库下，纯文字回答与带来源标注的架构图在"能否发现模块接口不匹配"上的差别。

定制三 · 持久记忆驱动的问 / 讲切换

解决：agent 不知道用户懂到哪一步，只能反复解释或默认全懂。

做法：跨会话维护用户的知识与经验评估，三态决定 agent 提问、讲解还是先问清储备本身。评估由一键蒸馏更新，用户可直接编辑。

对比示例：用户自陈某处不熟之后，前后两轮回复在详略上的变化。

五系统架构

core 负责调度与写权仲裁。UI、模型、tool call、state 分别作为接口插入 core，workspace 缓存会话数据。

八验收方案

  • 提前命中率。以真实实验设计记录作为标准答案，同一个模糊想法分别交给本 agent 与通用编码 agent，检验本系统是否在动手之前提出了切实的问题。该指标与干预次数一并报告。
  • 真实论文实验方法对照。将真实论文的场景与模糊 idea 交给 agent，验证 agent 设计方案与论文实验方案的匹配度。
  • 冷启动可用性。内置一组脱敏的 bootstrap 场景与案例，保证在没有个人积累的情况下首次打开即可用。
