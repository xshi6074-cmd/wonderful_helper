01

这张图要担的四件事

功能需求先写清楚，类型才有约束。四件事里任意一件被牺牲，这个结构就白设计了。

职责具体是什么它对结构提的硬要求
1 产物 模型当前推断的实验流程：步骤、顺序、分支、并行臂、对照组、测量点。要能画出来给人看。 拓扑必须是一等公民 —— 节点、边、嵌套。不能是平铺的键值表。
2 可改 用户直接在图上改：改名、加步骤、连线、断线、拖进分组、删掉。 每个可点选的东西必须有稳定 id。没有 id 就没有「改哪一个」。
3 可仲裁 同一轮里模型也在改。用户碰过的地方，模型基于旧值算出的结果作废。 每条 op 要能算出一组仲裁键，且键必须堵得住「换个 id 绕过去」。
4 可溯源 点开任一节点：谁写的、依据什么、多大把握、第几轮写的。没依据的画成虚线 —— 那正是盲区。 节点与边各自带一份 Prov，和图外推断共用同一套。

还有一句要求要单独拎出来：「结构可能非常灵活，不能用 mermaid 模板」。它约束的不是渲染，是词表 —— 节点类型、边类型、形状映射都不能写死在 Rust 的 enum 里，否则模型一想画「先并行三个配比、再挑一个往下走」就撞墙。灵活性的落点见第 2 节末。

02

中心决定：图是数据，mermaid 是产物

模型不画图 —— 它发图操作。mermaid 由我们从图纯函数地渲染出来，UI 和 prompt 拿的是同一份。

为什么不能让模型直接吐 mermaid

「模型每轮重画一张 mermaid」这条路走不通，不是因为难，是因为它和第 2、3 件事直接冲突：

  • 身份没了。第 N 轮模型写 B[退火]，用户把它改成「退火 400℃ 2h」，第 N+1 轮模型重画时又写 B[退火]。要认出这是同一个节点只能靠文本匹配 —— 而用户改的恰恰就是文本。用户一编辑，身份就断。
  • 仲裁退化成文本 diff。全量重写会让整张图看起来「哪儿都改了」，仲裁只能整份丢或整份收，「用户碰过的那一处」这个粒度不存在了。
  • 贵，而且越用越贵。图会长到几十个节点，每轮重画一遍是纯浪费的输出 token，还带着重写引入的伪改动。

所以：语义图是真相，渲染是它的纯函数

render::mermaid(&Graph) -> String 放在库里，Core 和 UI 调的是同一个函数。用户改个名字，图变了，渲染立刻变，不需要一次模型调用；重启之后渲染逐字节相同。模型的自由度在图上，不在像素上。

那「灵活」放哪

放在词表开放，不在文本自由。三个落点：

落点形式为什么够用
节点/边的类型kind: String，不是 enum 模型可以现造 parallel-arm、control、gate、abandoned。Rust 一个字都不用改。
形状与配色映射memory/prompts.toml 里的 [graph.shape] / [graph.class] 词表在持久层，用户随时可改，未知 kind 落到默认形状。这才是「不用模板」的真正落点 —— 改词表不用重编译。
渲染意向Graph.render: BTreeMap<String,String> 方言（flowchart / stateDiagram）、方向、自定义 classDef。渲染器不认识的键直接忽略，不报错。

模型画的那份也实现了，两种并存

Graph.sketch 收模型自己写的 mermaid 或 HTML 源码，Graph.view 决定当前以哪一份为准。两份同时存在，切过去再切回来，结构化那份原封不动 —— 跑起来看哪种在真实对话里更有用，不用现在定。

代价说死：能被结构化编辑的部分必须有稳定 id；模型要完全自由地画的部分，就放弃结构化编辑。Sketch 视图在 UI 上标注「不可点选」，用户只能整段改源码，整份在仲裁里只占一个键 flow/sketch。prompt 里也会明说这一条，让模型知道「想让用户能就地改，就把图搬回结构化视图」。

03

类型

在 src/state.rs。Workspace 长出一个 flow 字段，其余原样保留。

// 溯源三件套从 Field 里提出来，节点、边、图外推断共用一份。
// 这样 UI 的「点开看出处」对图内图外是同一段代码。
pub struct Prov {
    pub origin:     Origin,          // User / Model —— 由写它的事件类型决定，不可能丢
    pub source:     Option<Source>,  // Repo / Paper / User / Guess；None 视同 Guess
    pub confidence: Option<f32>,
    pub seq:        Seq,             // 最后一次写它的那条事件 —— 溯源，不是版本号
}

pub struct Node {
    pub id:     NodeId,                       // "n41_0"，见第 4 节
    pub kind:   String,                       // 开放词表：step / gate / measure / control / abandoned ...
    pub label:  String,                       // 图上显示的那行字
    pub body:   String,                       // 细节：这一步具体怎么做。图上折起来，点开才看
    pub attrs:  BTreeMap<String, String>,    // 参数：温度 / 转速 / 时长 / 样本量 / 仪器
    pub parent: Option<NodeId>,               // 分组、泳道、并行臂、对照组 —— 全靠它
    pub prov:   Prov,
}

pub struct Edge {
    pub id:    EdgeId,
    pub from:  NodeId,
    pub to:    NodeId,
    pub kind:  String,                        // next / branch / feeds / depends / alternative / invalidates
    pub label: String,                        // 条件：「若 XRD 无钙钛矿峰」
    pub attrs: BTreeMap<String, String>,
    pub prov:  Prov,
}

pub struct Graph {
    pub nodes:  BTreeMap<NodeId, Node>,       // BTree 而非 Hash：渲染必须逐字节确定
    pub edges:  BTreeMap<EdgeId, Edge>,
    pub render: BTreeMap<String, String>,    // 图级渲染意向，渲染器忽略不认识的键
    pub asides: Vec<Aside>,                   // 逃生舱：模型自由绘制，只读，不参与仲裁
}

pub struct Workspace {
    pub phase:  Phase,
    pub flow:   Graph,                          // 新增。图内：有拓扑的东西
    pub fields: BTreeMap<Path, Field>,       // 图外：没有拓扑的判断（第 9 节）
    pub open:   Vec<String>,
    pub parked: Vec<String>,
}

这个设计的最强论据：新增 0 个事件类型、0 张表

图的改动骑在已有的 Body::Edited{ops} / Body::Inferred{ops,dropped} 上，Graph 是 Workspace 的一部分因而自动进 checkpoint。折叠、恢复、分叉、去重、降级、仲裁一行都不用动。你上一轮担心的「图改得频繁、只存 diff 会重组很慢」也已经被现有机制答掉了：事件是 diff，checkpoint 是全量，从最近 checkpoint 重放只花 checkpoint_every 条事件。

04

id：Core 铸，形状自带溯源，永不复用

模型不许自己起 id —— 它会撞号，也会复活删掉的东西。分配 id 和分配 Seq 是同一类事：只有 Core 这个单线程信箱能做。

形状

NodeId("n41_0") = 创建它的那条事件的 seq + 批内序号。EdgeId("e41_1") 同理。

白拿两个性质：id 本身就说明「它是第 41 号事件写下的」，点它就能跳到那条事件；而 seq 单调 ⇒ 删掉的 id 永远不会被重新铸出来，「模型换个 id 把用户删掉的步骤原样加回来」这条路从形状上就断了。

别名：模型怎么引用还不存在的节点

模型发 $anneal 这样的别名，只在同一批 op 内有效，同批的边可以拿它当端点。commit 分配到 seq 的同时把批内所有 $ 引用替换成真 id，落进事件的只有真 id（不变量 I11）。

引用了一个不存在的真 id，或用了一个批内没定义过的别名 ⇒ 整条 op 丢弃并计入 dropped，不凭空创建。模型记错 id 是常事，凭空创建会造出一地没人要的孤儿节点。

分叉的角落：两条分支可能各自铸出 n41_0。它们在不同 session、永不共享一个 Workspace，所以运行时无害；但将来若要做「跨分支对比」，(session, id) 才是全局身份。先记着。

05

仲裁：键怎么算，三个漏洞怎么堵

现有机制不变：turn_edits 每轮清空，用户的 op 占键，模型的 op 查键，撞上就丢并计入 Inferred.dropped。要改的只有一件事 —— Op::path() 变成 Op::keys()，因为一条 op 可能占多个键。

op占用 / 查询的键为什么是这些
Set{path} · Remove{path}path图外推断，原样。
Node{id}flow/<id>元素级，见下方粒度决定。
Edge{id, from, to}flow/<id>
flow/<from>-><to>		第二个键堵漏洞 1。端点从 op 取，op 没带就从当前图里查。
Drop{Node(id)}flow/<id>
flow/label:<归一化 label>		第二个键堵漏洞 2。归一化 = trim + 去内部空白 + 小写。
Drop{Edge(id)}flow/<id>
flow/<from>-><to>		同上，端点从图里查。
Render{key} · Aside{id}flow/render/<key> · flow/aside/<id>渲染意向也可能被用户调，同样走仲裁。

三个漏洞

漏洞 1 用户删了一条边，模型用新 id 把同样的连接加回来

只按 id 比对完全挡不住 —— 新边的 id 从来没被占过。堵法：边的仲裁键里加一条有序端点对 flow/n12_2->n14_0。用户断开这条线时占的是这个键，模型换几个 id 都撞得上。

漏洞 2 用户删了一个步骤，模型新建一个同名节点把它复活

id 不复用挡住了「原样加回来」，挡不住「换个 id 重写一遍」。堵法：删节点时额外占一个归一化 label 键。这是启发式，模型换个措辞就绕过去了 —— 但代价方向是安全的：宁可多丢一条 op（模型下一轮从 dropped 里看得到、可以重提），也不要静默盖掉用户的删除。已开

漏洞 3 模型加一条边指向用户刚删掉的节点

不需要新机制：端点不存在的边在 Workspace::apply 里直接落不下去（不变量 I9）。已经堵住了。

粒度：到元素，不到属性

用户只改了 n14_0 的名字，模型同轮想给它加一条 temp=400℃ —— 一起丢。理由：用户改一个步骤的名字，往往意味着他对这一步的判断变了；让模型接着改它的参数会拼出一个前后不一致的节点。而且仲裁的误伤方向是安全的（模型能从 dropped 里看到、下一轮重提），漏判的方向不是。

不加 pin（永久锁）。locked: HashSet<Path> 已经被删过一次，理由现在仍然成立：用户填错一次就永久挡住模型。跨轮的保护本来就有 —— Prov.origin = User 会让 prompt 里出现 [用户设定] 标记，加上 system 段那句「改用户设定的东西之前先问」。那是约束，不是拒绝，改错了模型还能商量回来。

06

op 集合

图内的 op 全部是 patch：None = 这一项不改。这是「只改 label 不动 body」能成立的前提，也是把重写压到最小的地方。

pub enum Op {
    // ----- 图外（已有，只多一个 anchor）-----
    Set { path: Path, value: Value, anchor: Option<NodeId>,
          source: Option<Source>, confidence: Option<f32>,
          open: Option<Vec<String>>, parked: Option<Vec<String>> },
    Remove { path: Path },

    // ----- 图内（新增）-----
    Node  { id: NodeId, kind: Option<String>, label: Option<String>, body: Option<String>,
            parent: Option<Option<NodeId>>,          // Some(None) = 从分组里挪出来
            attrs: Vec<(String, Option<String>)>,     // 值为 None = 删这个 attr
            source: Option<Source>, confidence: Option<f32> },
    Edge  { id: EdgeId, from: Option<NodeId>, to: Option<NodeId>,
            kind: Option<String>, label: Option<String>,
            attrs: Vec<(String, Option<String>)>,
            source: Option<Source>, confidence: Option<f32> },
    Drop  { id: ElemId, why: Option<String> },        // why 见第 9 节
    Render{ key: String, value: Option<String> },
    Aside { id: String, title: String, lang: String, src: String },
}

pub enum ElemId { Node(NodeId), Edge(EdgeId) }

删除的连带效果（写在 apply 里，因而重放确定）

  • 删节点 ⇒ 连带删掉以它为端点的所有边。
  • 删节点 ⇒ 它的子节点提升到它的 parent，不级联删除。删一个「对照组」不该把组里三个步骤一起带走 —— 那是用户最不想要的意外。
  • parent 赋值若会成环，拒绝这一项（同批其余项照常生效）。嵌套深度上限 8。
07

用户在图上的一笔，变成什么

手势只在 apply 之后才产生真实改动 —— apply 之前是纯 UI 本地态，这条不变。apply 时走已有的 CoreMsg::Edit{ops}，落成一条 Body::Edited。

用户做的事op占的键
改节点标题Node{ id, label: Some(..) }flow/n14_0
编辑细节 / 参数Node{ id, body } · Node{ id, attrs }flow/n14_0
拖出一个新步骤Node{ id: $new1, label, kind: "step" }—（新的，无从冲突）
连一条线Edge{ id: $e1, from, to }flow/n12_2->n14_0
改接到别处Edge{ id, to: Some(..) }旧端点对 + 新端点对
断开Drop{ Edge(id) }flow/e13_0 + 端点对
删掉一个步骤Drop{ Node(id), why }flow/n17_0 + label 键
拖进 / 拖出分组Node{ id, parent: Some(Some(g)) } · Some(None)flow/n16_1
标注来源、调置信度Node{ id, source, confidence }flow/n14_0

一次 apply = 一条 Edited 事件 = 一次原子写入。用户在图上连拖带改十下再按 apply，落盘的是一条事件、一个 seq、一个回滚点。这也是除 turn 之外，用户唯一能自己划的回滚边界。

主场景是 ML，所以最有信息量的是架构图：数据 → 模块 → 算子 → 损失 → 指标 → 消融臂。形状来自 memory/prompts.toml 的默认词表，用户随时可改。实线 = 有实证来源（用户口述 / 论文章节 / 仓库位置）；虚线 = Source::Guess 或没标来源 —— 上图里冻结几层、温度系数、整组消融都是模型自己猜的，这一眼就是要给用户看的盲区。决策树刻意不主推：`gate` 留了个形状，但那类图本来就难画好，也不是 ML 讨论里信息量最大的东西。

prompt 里怎么拼

mermaid 之后跟一段明细，只写 mermaid 装不下的东西，且只写有内容的节点 —— 标题不重复第二遍，省 token：

== 实验流程 ==
<上面那段 mermaid，逐字节相同>

  body: 对称 InfoNCE，图文两个方向都算
  ↳ risk.negatives = 负样本数可能不够，用户没说过卡数
n12_2  [模型推断 · 模型推测 · conf 0.3]
  body: 冻结前 6 层是猜的，用户只说了「文本塔别全调」

== 本轮用户改过、你的改动被丢弃的位置 ==
flow/n14_0  （用户本轮刚改过它的标题）

图会涨，而折对话救不了图。渲染后的图算进 plan_compaction 的 fixed，图长到几十个节点会让折叠触发得越来越早，最后折无可折。答案不是折数据，是给模型的那份图按 detail 级别裁剪：已完成的分组只出标题、不出内部节点。数据一个字不动，只有渲染层多一个参数。列进欠账。

09

图外推断、锚点，以及放弃的路线

什么进图，什么不进

图内 · flow

有拓扑的。步骤、顺序、分支条件、并行臂、对照组、测量点、依赖。判据是一句话：它和别的东西之间有没有一条边。

图外 · fields

没有拓扑的判断。领域、目标、资源约束、样本量口径、用户偏好、风险。原来的 path → Field 原样保留，它没有被图取代。

Field 多一个 anchor: Option<NodeId>：一条图外推断可以挂到某个节点上（「这一步的温度依据不足」）。UI 在该节点旁显示一个角标，prompt 里跟在该节点的明细后面（见第 8 节）。不必二选一 —— 强行把所有判断塞进图，图会变成一张便签墙。

放弃的路线：不进图

这张图只服务正向决策。「试过没成立的方法」确实是这个项目里最值钱的数据（memory/project.md 就是这么写的），但把它画进图会直接抬高用户的阅读与决策成本 —— 图上每多一个灰掉的「这条走不通」，就多一份每次都要略过的东西。曾经考虑过 kind: "abandoned" 加 invalidates 边，否掉了。

它落在时间线上，不落在图上：

已实现 Drop{ why: Option<String> }

用户删掉一个节点后，UI 在原地留一个可跳过的单行输入「为什么去掉？」—— 不弹窗、不阻断，愿意写就白拿一行最值钱的数据。蒸馏扫时间线上的 Drop 事件去捞：图上删掉不等于历史里删掉。

以后再说

要给经验性内容一个位置的话，那是 explore mode 下的独立栏，不是这张图。等真跑起来看用户会不会想翻它。

10

不变量 · 欠账 · 三条已拍

三条新不变量（每个场景收尾时验，与 I1–I8 同处）

编号内容它能抓住什么
I9 图完整每条边的两端都在 nodes 里；parent 链无环、深度 ≤ 8。悬边、删节点后的残留、模型造出的环形分组。
I10 渲染是纯函数同一个 Graph 渲染两次逐字节相同；且 mermaid 里出现的 id 集合 等于 nodes 的 id 集合。「图上悄悄少了一个节点」 —— 没有这条，渲染吞掉一个节点是完全不可见的。
I11 无未解析别名时间线上任何一条 op 里都不存在 $ 前缀的 id。别名解析漏了一处，会在重放时变成一个永远指不到的引用。

这个设计新欠的账

  • 给模型的图要按 detail 裁剪。图涨到几十节点之前不痛，但迟早痛。
  • Built 视图的 HTML 渲染：render::built_html 已经占好位并写清了 TODO —— 逻辑与 mermaid 高度相似（同样按 id 序遍历、递归展开子图、查形状、按 prov 决定虚实），差别只在产出 DOM 而不是 mermaid 文本。现在不写是因为节点组件长什么样由 R2 的 UI 决定，此刻等于凭空猜。Sketch 的 HTML 已经能用（模型自己写的源码原样出去），所以这条路不是空白。
  • UI 侧的图编辑器本身属于 R2，这份只定到「一笔手势等于哪条 op」为止。
  • 归一化 label 键的误伤率没有数据支撑，得跑起来看 dropped 里有多少是冤的。
