# Pre-test（草稿）

在实现前明确“哪些行为必须成立，什么错误必须被发现”。按场景投入验证工作；不要把写了多少测试当作质量目标。使用中的具体失效案例可以帮助修订本草稿。

## 先决定使用场景

读用户目标、现有接口与测试、代码用途及运行成本；复用已知信息，不为了填写表格重复提问。

| 场景 | 默认投入 |
| --- | --- |
| 产品代码、agent／工具服务、可复用库与长期维护基础设施 | 先写关键行为与失败场景的测试，再实现相关行为；重点覆盖接口、状态迁移、外部交互与有代价的副作用 |
| 一次性实验／探索脚本 | 优先做数据与配置检查、关键不变量、小样本冒烟和可追溯运行记录；不默认搭完整测试框架或强制全套 TDD |
| 实验中的共用数据加载、划分、mask／loss／指标、缓存或恢复模块 | 为会影响多个实验或结论的确定性行为写少量针对性测试，投入随复用与失效代价增加 |
| 低影响、可逆的小改动 | 复用现有检查或直接验证；没有具体风险时不添加仅复刻实现的测试 |

判断依据是用途、复用和失败后果，不能只按文件名或“科研项目”标签决定。实验代码也可能需要关键回归测试；产品代码也不需要为每个细枝末节造测试。模型效果、消融收益与泛化能力由实验协议检验，不能用单元测试替代。

## 从行为构造覆盖面

先确定当前改动的输入、输出、状态、副作用与已有验收约定。沿用用户给出的 part／接口边界；没有约定的关键项列为待定，并说明它怎样影响测试。

- 从用户可见行为和失败影响提出用例，不从现有实现逐行倒推断言。对每个关键场景写清输入／前置状态、动作、可观察结果、禁止发生的副作用，以及判断结果的依据。
- 产品／agent 场景按实际相关性考虑：正常路径、非法／空输入、工具失败或超时、部分成功后的重试、取消与预算耗尽、状态恢复，以及重复操作的幂等性。只选此次功能涉及的项。
- 实验场景按实际风险考虑：数据筛选和时间可用性、划分隔离、样本数、shape／mask／单位、loss 和指标的确定性计算、关键梯度路径、配置与结果对应。不要测试每个张量算子或为探索中的所有候选路线提前造套件。
- 用契约、可手算的小例子、可信参考或不变量作为预期值来源。避免从被测函数复制计算结果作为答案。随机／LLM 输出优先检查协议、动作约束、状态和失败处理，不锁死措辞。
- Mock 外部边界以控制故障和成本，但保留被测行为。若关键路径被 mock 掉，明确还缺哪项集成验证；纯单元测试通过不等于真实链路通过。

产出与任务大小相称的行为清单；复杂任务可用“需求／场景 → 预期与不允许发生的事 → 验证层次 → 成本与时机”的表。标出哪些关键测试先做，哪些需要后续集成或真实运行。不要给没有依据的覆盖率或用例数指标。

## 产品功能：关键测试先行

当用户只要求设计测试时，交付测试方案，不自动进入实现。已获授权开发时，按关键行为小步推进：

1. **写测试并确认合理的失败。** 若缺接口，可先建立最小接口桩。确认测试因目标行为缺失或错误而失败；语法、导入、环境故障不算完成行为验证。
2. **实现使目标测试通过的行为。** 通过可观察结果检验完成程度，不用无断言的运行、总是成功的占位检查或过宽的异常捕获充数。
3. **运行相关回归与必要集成检查。** 对有价值的测试，可用一个针对性的错误变体／反例检查它是否真的会失败；不默认跑昂贵变异测试或无关全仓库检查。

实现期间修改验收测试，要说明：原测试是否误解契约、需求是否变化、还是发现新边界。不要仅为迁就当前实现放松断言；有争议的关键验收变更保留为未决项。用户明确更改需求后同步测试，不把测试冻结成不可修改的规则。

已有 bug 优先写可重现它的回归测试，再修复。若环境阻塞或暂时无法执行，保留测试方案／代码，明确未运行，不伪称经历了 red／green。

## 实验脚本：按结论风险验证

从“这个错误会不会改变样本、对照或结论”决定检查重点。简单实验可在脚本中用明确断言／数据统计、已验证函数和一个小样本端到端冒烟满足需求，不默认新建测试目录。

分开确认：**数据协议成立、计算／流水线可运行、实验效果是否支持假设。** 冒烟通过只支持前两类的有限范围，不支持效果结论。需要比较效果时，写清固定项、对照、共同指标、判据与预算，交给实验设计与消融处理。

## 交付与迭代

沿用现有计划、测试目录和结果记录位置；与用户已有交付格式、复现入口和对齐时点一致。约定不足时说明关键缺口，并给合理候选；不把建议标成已协商完成。

简述本轮采用的验证投入、关键覆盖、实际失败／通过证据，以及暂未覆盖的边界和原因。以“刻意做错哪个关键行为，现有验证还能通过吗”检查 lazy tests。按使用中出现的具体遗漏修订，避免把每次偶发问题扩成通用流程。
