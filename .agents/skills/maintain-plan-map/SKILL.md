# 逐轮规划图

维护一张能承接工作的图：让用户看清各 part 的目的、实际路径、关键选择、依据、验收方式与未决项。让没有参与前文的执行者知道哪里已确定，哪里仍须查证、选择或实测。

## 1. 从用户的 parts 开始

- 先读取用户本轮要求、已有规划图和相关材料。沿用用户给出的 part 名称、边界与大体规划，不按“数据／模型／评测”之类模板替用户重新分组。
- 先识别每个 part 要解决的问题、拟采用的路线、产物及与其他 part 的接口。发现明显遗漏时提出具名的新增／拆分建议，标为“建议”，保留原结构。
- 若用户尚未给 parts 或逐 part 方向，先画现有信息支持的局部图；把缺失的大体规划写为未决项。可给候选拆分，但不要把它标为用户已选方案。只询问当前确实影响推进的一项，继续处理独立部分。
- 尊重用户直接编辑的节点、文字与决定。发现冲突时保留其原值，指出具体分歧；用户本轮已要求修改时直接执行，不重复确认。
- 区分规划与执行。调用本 skill 只授权维护图及明细；按用户另行授权执行工作，不因画出实验分支就自动训练、下载大数据或运行全部消融。

## 2. 维护一个权威文件

优先更新已有规划图文件；没有时，在当前项目使用 `docs/plan-map.md`。文件名冲突时沿用用户指定的位置。文件中同时保存 Mermaid 图、节点明细、未决项与少量有意义的修订记录，不另建一套内容重复的 JSON 或工作记忆。

初建时参考 [规划图骨架](assets/plan-map.template.md)，按实际需要删减；模板字段完整不等于设计完整。实验任务还要读 [实验细节规则](references/experiment-detail.md)。需要参照具体画法时读 [风速任务示例](references/example-wind-plan.md)；示例中的提案与占位符不是用户的项目事实。

采用两层视图，保持为同一张逻辑图：

1. **总览**：表达用户的 parts、关键产物、真实依赖、并行路线和决定去向的分支。不要只把几个层面串起来。
2. **局部展开**：展开本轮涉及的 part，画到数据、模块、必要算子、训练／状态更新、对照、评测或交付动作；在图中挂出改变路线的未决项。让总览和展开图共享对象 ID，并明确展开对应哪个 part。

给对象稳定 ID，例如 `P1`、`P1_SPLIT`、`P2_ENCODE`、`E_FEATURE`、`Q_SPLIT`。用户提供 ID 时沿用。语义未变就保留 ID；新增对象追加 ID；合并／替换对象时记录旧 ID 的去向。用文件中的记录标题让 ID 可定位。

按对象安排细节：

| 对象 | 图中呈现 | 同 ID 明细中补足 |
| --- | --- | --- |
| Part／动作 | 实际步骤、关键输入输出、依赖 | 目的、大体路线、必要操作、接口、交付物、验收方式 |
| 模型／算子 | 插入位置、数据流、监督／状态关系 | 形状与轴含义、参数共享、训练／冻结、梯度、尺度和更新顺序，按相关性填写 |
| 实验分支 | 基线与变体、汇合评测、串行／并行 | 要检验的假设、只改什么、固定什么、指标与判据、预算与运行证据 |
| 未决项 | 影响路线的分支或挂到相关节点的虚线 | 缺什么、影响范围、候选与建议、已有依据、如何解决、结果怎样改变路线 |
| 决定／观测 | 影响拓扑时入图，否则锚定明细 | 选择与理由、来源、适用条件、替代解释、复核触发条件 |

不要把所有文字塞入图，也不要把重要细节全部藏在正文。图里必须看见真实操作与选择，明细承载图中放不下的依据和接口。

## 3. 标明依据、选择与进展

分别记录三个维度，避免把“讨论过”当成“做成了”：

- **方案状态**：用户指定／建议／暂定／未决／弃用。
- **执行状态**：未开始／进行中／已实现／已运行／已验证／需复核。只把有实际证据支持的验收标为已验证，并写明验证范围；一次运行不证明一般效果。
- **依据类型**：用户要求、已读代码、已读文献、运行观测、待验假设。记录真实位置或产物；没有依据就写缺口，不虚构精确数值、时间或置信度。

在图中显式标出“建议”“暂定”“未决”“需复核”等会改变理解的状态；其余详细来源放在锚定记录。把用户要求当约束，把用户效果猜想当待验假设。把代码实现、实验观测与机制解释分开。

让调研服务于决定：记录“哪个候选／前提被什么事实影响，下一步因此怎样变”。只新增名词而没有决策影响时，不把它写成路线已确定。

对未决项使用稳定 `Q_...` ID，并区分：

- **查证**：读取能决定该项的材料；不可读时保留缺口。
- **用户选择**：针对目标、边界、偏好或重大资源取舍给候选及后果；只暂停依赖该选择的分支。
- **实测**：画出最小可区分实验及结果分支；低成本可逆默认可标“暂定”，用户未反对不等于已经接受关键设计。

给每个未决项写清：所影响的节点、当前缺口、候选／建议及依据、解决动作、判定条件、下一次复查时点。暂无可靠判据就明确“判据待定”，不要用看似专业的阈值补空白。

## 4. 每轮按实际进展更新

把文件与本轮输入对照后再写，保留用户从上一版到本轮的修改。

1. 提取新增事实、结果、选择、纠正、阻塞与进度；区分实际发生和拟议动作。
2. 按 ID 局部修改节点、边、明细和未决项。没有实质变化时说明“本轮图无实质变更”，不制造空修订或重画整图。
3. 沿实际依赖复查下游：目标、数据、接口或状态变了，就检查 loss、对照、指标、验收与交付。标出具体哪些旧结果“需复核”，保留原配置和证据；不要删掉不方便的负结果。
4. 将已解决的未决项写成带来源的决定，移出当前未决清单，在修订记录保留 ID 与去向。被搁置的项记录原因和重新启用条件。
5. 追加一条有意义的修订摘要：改变什么、依据是什么、影响哪些 ID、下步由谁或什么证据决定。不为每条聊天或措辞变化记流水账。

在每次设计或进展对齐结束时，使本轮受影响的图与明细保持最新。对新 part、新实验臂或新疑点追加局部，不为了保持原图美观抹掉它们。

## 5. 画图与验收

- 默认使用 Markdown 中的 Mermaid `flowchart TD`。需要精确表达状态迁移或时序时可选相应图型；不引入 UI、ELK、数据库、自动蒸馏或自建执行器。
- 用 `subgraph` 组织 part 或实验臂，真实包含才使用包含关系；相关但独立的部分用带语义的边连接。
- 为边写清数据、监督、依赖、比较或分支条件。虚线用于未决／暂定关系，并附文字；不要只靠颜色或线型表达意义。
- 引用带标点的标签，使用短标签，不使用 HTML 标签、click 指令或每图配置。任一水平层最多五个节点；图大时按 part 展开，不画无法阅读的一张巨图。
- 检查所有 ID、引用、边和展开都能定位；检查数据到结论的路径是否完整，消融臂是否有可比的汇合评测，未决项是否真实可见，陈旧结果是否标出。
- 若有 Mermaid 渲染工具，验证语法并查看可读性。若没有，检查源码并如实说明未做渲染验证；不要为了渲染安装新应用。图语法通过不代表设计正确。
- 用“执行者还需要自行发明什么会影响结果的决定”检查相关 part。把缺口补成有依据的细节、条件分支或明确未决项，避免“按常规”“合理划分”“充分消融”等空话。

交付可编辑的权威文件，并在对话中展示本轮新增／受影响的图；没有变化时不重复展示整张图。正文只说明本轮关键改变、证据边界和下一个最有决策价值的动作。不要只给文件链接，不要用完整检查清单淹没用户。
