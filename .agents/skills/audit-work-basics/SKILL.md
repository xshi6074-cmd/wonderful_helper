# 基本盘审计（草稿）

作为审计者检查“约定—实际产物—证据”是否对应。把发现交给协作者处理，不以审计之名重定项目路线。先在真实任务中使用，再依据暴露的具体遗漏修订本草稿。

## 确定本轮范围与依据

- 从用户要求、已有规划图、交付约定和相关代码／配置／结果中识别本轮要核查的 part、版本与交付节点。沿用用户 parts 和已有 ID。
- 优先检查本轮变更及受其影响的下游。材料不足时，先完成可核查的部分，再指出需要什么；不要默认审完整仓库或运行全部实验。
- 分清三类发现：**实际违约**（已有明确约定而产物不满足）、**约定缺口**（影响执行但尚未决定）、**证据缺口**（提出结论却没有相应验证）。“没写进文件”不自动等于“没做”；约定缺失也不自动判为违约。
- 冲突时列出原约定与实际行为，不把审计者的新建议冒充用户要求。效果猜想不是验收标准；计划、实现、运行与验证分别核查。

## 按任务选择审计面

只检查实际相关的项目，不把下面的维度扩成必须全部填写的清单。

| 审计面 | 需要确认的事实 |
| --- | --- |
| 交付与对齐 | 交付物、格式、位置、复现入口、阶段验收、负责人／下一步和对齐时点是否约定；实际交付是否对应，延期或范围变化是否说明 |
| 文件与版本 | 权威文件是否可辨；代码、配置、数据版本、运行记录与结果能否对应；临时文件与交付物是否混杂；负结果和被替代结果是否保留其去向 |
| 验证与测试 | 验收行为是否被实际检查；测试是否有能发现错误的断言；是否大量 mock 绕开关键路径；修改测试是否改变了原验收含义；证据适用到什么范围 |
| 数据与评测 | 筛选／排除规则、划分单位、时间可用性、泄漏风险、样本量与关键子集是否交代；训练和评测是否遵循同一有效协议 |
| 消融与结论 | 每臂的假设、只改项、固定项、共同评测、串并行条件、预算与有效性判据是否清楚；运行证据是否支持归因，是否遗漏负结果或夸大单次收益 |

实验审计以结果可比较、可追溯为重点。一次性实验脚本缺少完整单元测试套件本身不是问题；某个数据处理或指标错误会影响结论却未检查，才是具体风险。只有用户将实验部分纳入本轮范围时，才核查相应细节。

## 查验而不是复述

- 不把执行者总结直接当证据。选取能支撑关键结论的原始材料：相关代码位置、运行配置、命令与日志、结果表／预测产物、数据统计及其版本。
- 对每个发现写出：依据位置、观察到什么、与哪项约定或判断相关、可能造成什么具体影响。审计者推断与已核实事实分开。
- 已获授权范围内，可做低成本核查或复现已有检查。昂贵训练、全量消融、修改交付物不因调用审计 skill 而自动获得授权；将必要动作写为建议。
- 若用另一执行上下文检查，传入需求、相关原始产物与约定，不把“预期审计结论”当任务提示。没有独立上下文时，不宣称这是独立审计。
- 用不满足原验收的反例检验测试力度：错误输入、错误状态、关键副作用或失效协议是否仍可能通过。仅报告“测试全绿”或覆盖率数字不能证明行为已覆盖。

## 给出可处理的审计结果

按实际影响排序：会使交付／结论无效或阻塞下一步的问题，优先于局部改进。没有可靠证据时写“待核实”，不虚构置信度或严重程度分数。

使用现有位置和对象 ID；必要时为发现给稳定 `A_...` ID。每项尽量包含：

**状态与对象 → 证据位置 → 具体缺口及影响 → 最小修正／取证动作 → 如何确认已解决。**

把建议标为待定、已接受或已拒绝；只依据用户真实选择更新状态，保留有意义的理由。审计建议不因无人反对而成为约定。默认交付审计发现；只有用户要求修正时才修改被审计的产物。

报告末尾简述核查范围、无法核查的部分及本轮最值得处理的下一项。没有发现问题时说明检查边界，不宣称项目整体无缺陷。沿用已有记录文件；不为了每次审计建立新的协议文档或庞大流水账。
